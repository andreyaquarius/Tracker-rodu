# Аудит безпеки «Трекера Роду»

Дата перевірки: **14 серпня 2026 року**  
Перевірений commit: **`4645b47`**  
Обсяг: React/Vite-клієнт, Supabase/PostgreSQL/RLS/Storage, 18 Edge Functions, PDF-worker, GitHub Actions, браузерне зберігання, залежності та конфігурація production-сайту.

## Підсумок

У перевіреній версії **не знайдено ознак активного витоку даних**, відкритих публічних таблиць або закомічених робочих секретів. Базовий серверний контур побудовано правильно: на всіх 61 таблицях `public` увімкнено RLS, сховища приватні, а доступ до проєктних даних перевіряє членство та роль у проєкті.

Водночас стан системи ще не можна назвати «максимально захищеним». Знайдено одну критичну для цього застосунку залежність, два високі ризики локальної приватності та декілька середніх ризиків конфігурації. Крім того, поточна архітектура не є zero-knowledge: база, серверні функції та облікові записи з `service_role` технічно працюють із незашифрованими прикладними даними. Тому буквальна гарантія «ніхто, крім користувача» зараз неможлива.

Для спільних проєктів правильною межею доступу є: **власник та лише явно запрошені ним редактори/глядачі**. Адміністратор бачить звернення до підтримки за задумом функції, але не повинен автоматично отримувати доступ до родоводів.

## Модель загроз

Захищаються:

- особи, родинні зв'язки, події, місця, примітки та власні поля;
- завантажені документи, фотографії, резервні копії та GEDCOM-файли;
- посилання на зовнішні джерела та Google Drive;
- API-ключі ШІ, OAuth-сесії та токени авторизації;
- приватні звернення користувачів до адміністратора.

Перевірені класи атак:

- неавторизований відвідувач;
- авторизований користувач, який намагається прочитати чужий проєкт;
- редактор/глядач, який перевищує надану роль;
- шкідливий PDF, XSS та викрадення браузерної сесії;
- SSRF через зовнішні URL документів і фотографій;
- помилка або компрометація CI/CD чи залежності;
- залишки приватних даних на спільному пристрої;
- зловживання привілейованим серверним ключем.

## Критичні та високі ризики

### SEC-01 — Уразлива версія PDF.js при роботі з недовіреними PDF

**Рівень: критичний для контексту застосунку.**

Обидва lock-файли фіксують уразливі версії `pdfjs-dist`: `6.0.227` у `package-lock.json` та `6.1.200` у `pnpm-lock.yaml`. Вони входять у діапазон `< 6.2.108` для [GHSA-hq66-cqwq-w95j](https://github.com/advisories/GHSA-hq66-cqwq-w95j), який описує виконання JavaScript під час відкриття спеціально сформованого PDF.

Ризик тут підвищений, бо переглядач навмисно відкриває зовнішні й завантажені користувачами архівні PDF. У викликах `pdfJs.getDocument()` у `src/components/DocumentWorkspaceViewer.tsx:551` та `:564` немає захисних параметрів `enableScripting: false` і `isEvalSupported: false`.

Необхідно:

1. Оновити `pdfjs-dist` щонайменше до `6.2.108` в обох lock-файлах.
2. Додати `enableScripting: false` та `isEvalSupported: false` в обидва шляхи завантаження PDF.
3. Додати регресійний тест, що обидва параметри завжди передаються PDF.js.
4. Після оновлення повторити тест великих PDF, JPEG2000/JBIG2, range-завантаження й експорту сторінок.

Критерій закриття: production-збірка не містить версії з уразливого діапазону, `npm audit --omit=dev` не показує цю advisory, а тест заборони PDF-скриптів проходить.

### SEC-02 — Приватні дані залишаються в браузері після втрати сесії

**Рівень: високий.**

Клієнт кешує значні частини проєкту в `localStorage` під префіксом `tracker-rodu-project-`, а Supabase-сесія зберігається через `persistSession: true` (`src/services/supabaseAuth.ts:98`). Це нормально для UX, але збільшує наслідки XSS та ризик на спільному комп'ютері.

Явний вихід очищає кеш лише **після** `await signOutFromSupabase()` (`src/App.tsx:2371–2380`). Якщо мережевий вихід завершується помилкою, виконання переходить у `catch` і приватний кеш лишається. Обробник події `session === null` (`src/App.tsx:1082–1091`) скидає React-стан, але не очищає проєктні кеші та кеш документів. Отже, завершення/відкликання сесії або зміна облікового запису може залишити дані попереднього користувача на пристрої.

Необхідно створити єдину функцію `clearSensitiveBrowserState()` і викликати її:

- у `finally` під час ручного виходу;
- при отриманні `session === null`;
- при зміні `user.id` між сесіями;
- після втрати доступу до проєкту та завершення password-recovery flow.

Вона має чистити проєктні `localStorage`-ключі, IndexedDB документів, Google Drive-сесію, тимчасові blob URL та пам'яттєві кеші дерева. Серверний sign-out не повинен бути передумовою локального очищення.

### SEC-03 — До 500 МБ документів зберігаються у незашифрованому, не прив'язаному до користувача IndexedDB

**Рівень: високий.**

`src/services/documentBlobCache.ts` створює базу `tracker-rodu-document-cache`, зберігає повні `Blob` документів і допускає кеш до 500 МБ. Ключі записів не містять обов'язкової прив'язки до `user_id`, а `clearDocumentBlobCache()` не викликається під час виходу. Дані доступні коду того самого origin і залишаються після завершення сесії.

Необхідно:

- за замовчуванням не зберігати приватні документи постійно або зробити кеш явною opt-in функцією;
- мінімум — namespace `user_id/project_id`, короткий TTL, очищення при виході/зміні користувача/втраті дозволу;
- не кешувати signed URL і токени;
- для посиленого режиму застосувати клієнтське AES-256-GCM шифрування, усвідомлюючи, що воно не захищає від XSS під час активної розшифрованої сесії.

### SEC-04 — Немає наскрізного zero-knowledge шифрування

**Рівень: високий відносно заявленої вимоги приватності; це архітектурний розрив, а не окрема помилка коду.**

RLS захищає одного звичайного користувача від іншого, але PostgreSQL, Edge Functions, фонова обробка та власники привілейованих ключів технічно можуть працювати з відкритими даними. Тому зараз неможливо чесно гарантувати, що навіть оператор інфраструктури ніколи не зможе прочитати родовід.

Для буквального виконання вимоги потрібен окремий проєкт end-to-end шифрування:

- випадковий ключ даних (DEK) для кожного проєкту;
- AES-256-GCM для записів і файлів у браузері до відправлення;
- обгортання DEK окремо для власника та кожного запрошеного учасника;
- ротація ключів після відкликання доступу та безпечний recovery key;
- сервер зберігає лише ciphertext.

Це змінить серверний пошук, статистику, ШІ-аналіз, імпорт/експорт GEDCOM і фонові задачі: їх треба переносити на клієнт або в окремий контрольований контур розшифрування. Потрібне окреме ТЗ і моделювання відновлення доступу, інакше користувач може безповоротно втратити дані.

## Середні ризики

### SEC-05 — Storage дозволяє надто великі та довільні типи вкладень

Bucket `project-attachments` приватний і має коректні політики членства/ролей, але міграція `supabase/migrations/202606090002_storage.sql` задає ліміт **2 ГБ** на об'єкт і не задає `allowed_mime_types`. Клієнтська перевірка не є захистом: авторизований редактор може звернутися до Storage API напряму.

Потрібно встановити серверний allowlist MIME/розширень, реалістичний ліміт одного файла, квоту на проєкт/користувача, антивірусне сканування та карантин до завершення перевірки. Файли треба віддавати як attachment або з безпечним `Content-Type` і `X-Content-Type-Options: nosniff`.

### SEC-06 — На production-сайті бракує захисних HTTP-заголовків

Жива відповідь GitHub Pages має `200`, але не віддає HSTS, `X-Content-Type-Options`, `Permissions-Policy`, COOP/CORP та захист від вбудовування сторінки. Збірка додає CSP через `<meta>`, однак `frame-ancestors` [не підтримується в meta CSP](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/frame-ancestors), тому залишається ризик clickjacking.

Рекомендація: поставити домен за Cloudflare або перенести статику на хостинг із керованими заголовками й додати HTTP CSP з `frame-ancestors 'none'`, HSTS після перевірки всіх субдоменів, `nosniff`, строгий Referrer-Policy та мінімальний Permissions-Policy. `frame-src https:` і `img-src https:` варто замінити allowlist-ами реально підтримуваних постачальників документів.

### SEC-07 — Частина CORS та публічний registration guard мають fail-open поведінку

PDF gateway і GEDCOM-photo proxy мають строгі origin/host перевірки. Натомість `supabase/functions/_shared/ai.ts` повертає `Access-Control-Allow-Origin: *`, якщо `APP_URL`/`ALLOWED_ORIGIN` відсутні, а `registration-guard` свідомо має публічний CORS `*` без власного rate limit.

Deployment уже перевіряє потрібні змінні, але runtime має відмовлятися запускати приватні AI-функції без allowlist, а не відкривати CORS. Для registration guard потрібні Supabase rate limits, CAPTCHA/Turnstile і моніторинг аномального трафіку.

### SEC-08 — CI/CD використовує рухомі major-теги Actions і два різні lock-файли

Workflow-и використовують `actions/checkout@v6`, `actions/setup-node@v6`, Pages actions і `supabase/setup-cli@v2`, а не immutable commit SHA. Це створює supply-chain ризик. Також `package-lock.json` та `pnpm-lock.yaml` фіксують різні версії ключових залежностей, тому локальна та production-збірки можуть відрізнятися.

Потрібно обрати один package manager/lock-файл, зафіксувати Actions за повними SHA, додати Dependabot/Renovate, `persist-credentials: false` для checkout після непотрібності Git-токена та `npm ci --ignore-scripts` там, де lifecycle scripts не потрібні.

## Низькі ризики й технічний борг

- `react-router`/`react-router-dom` `7.18.1` входить у [GHSA-qwww-vcr4-c8h2](https://github.com/advisories/GHSA-qwww-vcr4-c8h2). Проблема стосується нестабільних RSC API, яких цей SPA не використовує, але залежність треба оновити до `>= 7.18.2`.
- `supabase db lint` повідомляє про неточні volatility-маркери (`STABLE`/`IMMUTABLE`), залежності від `pg_temp` у функціях дерева і можливе завершення `process_legacy_gedcom_cleanup` без `RETURN`. Ознак обходу доступу через це не знайдено, але функції слід виправити й додати SQL-тести на всі шляхи виконання.
- Для GitHub Actions та Edge Functions потрібна політика зберігання логів і автоматичне маскування URL-параметрів, signed URL, токенів та персональних даних. Під час вибіркової перевірки витоку таких значень не підтверджено.

## Підтверджені сильні сторони

- На **61 із 61** таблиць схеми `public` увімкнений RLS.
- Усі 98 локальних міграцій присутні у віддаленій історії до `202608130004`.
- Прямого анонімного читання родоводів не знайдено; доступ заснований на членстві в проєкті та ролях owner/editor/viewer.
- Приватні звернення підтримки бачать автор і адміністратор відповідно до призначення функції.
- Перевірені `SECURITY DEFINER` функції мають зафіксований `search_path`.
- Buckets документів, резервних копій і GEDCOM-експортів не є public; завантаження експорту видається через короткочасне підписане посилання.
- GEDCOM-photo proxy дозволяє лише HTTPS/443 і конкретний host, обмежує redirects і розмір відповіді.
- PDF-worker використовує HMAC, DNS-resolution із забороною приватних IP, IP pinning, allowlist redirect-ів, обмеження часу/розміру та тимчасові файли.
- Google Drive використовує scope `drive.file`; access token не зберігається у `localStorage`.
- У репозиторії та перевіреній історії не знайдено підтверджених робочих секретів. Vite/Supabase publishable keys є публічними за дизайном, але Google browser API key все одно має бути обмежений HTTP referrer та конкретними API.
- GitHub workflow permissions задані явно й переважно мінімально.

## Що обов'язково перевірити вручну в Supabase/Google/GitHub

Ці налаштування не можна достовірно підтвердити лише з репозиторію:

- MFA/TOTP для власника Supabase, GitHub, Google Cloud і доменного реєстратора;
- leaked-password protection, підтвердження email, мінімальна довжина пароля, CAPTCHA та Auth rate limits;
- точний Site URL і redirect allowlist без wildcard та production-`localhost`;
- обмеження максимальної тривалості/бездіяльності сесії;
- відсутність старих/невикористаних PAT, service keys, deploy keys і OAuth clients;
- branch protection, required reviews/checks, signed releases, GitHub secret scanning/Dependabot;
- актуальний Supabase Security Advisor;
- PITR/резервні копії та документована контрольна перевірка відновлення;
- audit log доступу адміністратора/фонового сервісу до приватних даних;
- Google OAuth consent verification, мінімальні scopes та точні Authorized JavaScript origins.

Орієнтир: [Supabase production checklist](https://supabase.com/docs/guides/deployment/going-into-prod) та [офіційна документація Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security).

## Межі цього аудиту

Це статичний і локальний динамічний аудит перевіреної версії, а не зовнішній penetration test. Він не доводить відсутність усіх вразливостей і не перевіряє значення production-секретів, внутрішні налаштування хмарних акаунтів чи фізичний доступ до пристрою. Після закриття P0/P1 потрібні повторний аудит і незалежне тестування з дозволеним staging-середовищем.
