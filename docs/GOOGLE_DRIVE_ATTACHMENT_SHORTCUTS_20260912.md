# Вкладення Google Drive без дублювання файлів

## Поведінка

- «Обрати з Google Drive» і посилання Google Drive прикріплюють оригінал. `storagePath`, ресурсний ключ і дані джерела належать оригіналу, а не ярлику.
- У цільовій папці активного проєкту (з урахуванням `driveFolderPath`) створюється `application/vnd.google-apps.shortcut`. Відомості про ярлик зберігаються окремо в `driveShortcutId` / `driveShortcutFolderId`. Міграція БД не потрібна.
- Перед створенням перевіряються всі сторінки списку ярликів папки за ID цільового файлу. Повторне прикріплення використовує доступний наявний ярлик. Якщо оригінал уже в цільовій папці, ярлик не створюється.
- Одночасні запити в одній вкладці об’єднуються; за підтримки Web Locks перевірка та створення серіалізуються між вкладками цього сайту. Це не глобальна транзакція між різними пристроями: Drive не має унікального обмеження на пару папка/ціль.
- POST створення ярлика не повторюється автоматично після мережевої помилки. Спочатку перевіряється, чи ярлик уже створено. Немає резервного шляху копіювання файлу.
- Якщо ярлик створити не вдалося, прикріплюється оригінал і показується попередження. Помилка зміни проєкту/облікового запису не ігнорується: потрібно вибрати файл заново.
- Вибір ярлика в Google Picker розкриває його до оригіналу. Оригінал і ярлик на нього не утворюють два вкладення в одному полі.
- Від’єднання видаляє тільки зв’язок у записі. Оригінал не видаляється навіть при `force`. Ярлик теж залишається: ним можуть користуватися інші записи. Це також стосується скасування форми — безпечніше залишити ярлик, ніж видалити спільне посилання.
- Завантаження з комп’ютера, скриншоти та явне «Зберегти копію у Google Drive» для зовнішніх GEDCOM-фото залишаються створенням нового файлу.

Початковий Picker-шлях уже прив’язував файл за ID без копіювання. Ця зміна додає організацію ярликами, обробку вибору ярлика та регресійні перевірки. Вона не видаляє наявні дублікати й не доводить, яким саме попереднім шляхом вони були створені.

## Доступ і безпека

Обсяг OAuth залишається `drive.file`; нових широких дозволів немає. Оригінал не переміщується, не перейменовується, не копіюється; дозволи оригіналу не змінюються. Ярлик не надає іншим учасникам доступ до цільового файлу автоматично. Видалення оригіналу або відкликання доступу може зробити вкладення недоступним.

Офіційні джерела: [ярлики Drive](https://developers.google.com/workspace/drive/api/guides/shortcuts), [ресурсні ключі](https://developers.google.com/workspace/drive/api/guides/resource-keys), [створення файлів і обмеження попередньо згенерованих ID](https://developers.google.com/workspace/drive/api/guides/create-file).

## Перевірки

Автоматизовані сценарії: metadata-only POST, незмінність ID і батьків оригіналу, повторне та одночасне прикріплення, пагінація ярликів, однакові назви різних файлів, різні підпапки, загублена відповідь, заборона створення ярлика, ресурсні ключі, неробочі/циклічні ярлики, від’єднання без DELETE, зміна проєкту, відкриття PDF за ID оригіналу.

Локальна перевірка: `npm test` — 2432 пройшли, 5 пропущено, 0 помилок; `npm run build` — успішно (наявне попередження про великі JS-бандли); `git diff --check` — без помилок форматування.

Ручна перевірка з реальним Drive перед публікацією:

1. Запам’ятати ID та папку тестового PDF/фото поза папкою проєкту.
2. Прикріпити через «Обрати з Google Drive», зберегти запис. У папці проєкту має бути ярлик; оригінал має попередній ID та папку.
3. Прикріпити той самий файл до іншого запису з тією самою цільовою папкою — другого ярлика бути не має.
4. Вибрати оригінал і ярлик разом: у полі має бути одне вкладення. Перевірити перегляд і завантаження.
5. Від’єднати файл, зберегти та прикріпити знову. Оригінал і ярлик мають зберегтися, нової копії бути не має.
6. Повторити для Google Docs у модулі документів і для запису з цільовою підпапкою.

Автоматизовані тести використовують підміну Drive API та не змінюють користувацький диск. Перевірка з живим OAuth/Google Picker, коміт, пуш і деплой у цю роботу не входили.
