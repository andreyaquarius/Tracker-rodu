# Таймаути пошуку «Загуляк»: виправлення 07.09.2026

Міграція: supabase/migrations/202609070001_zagulyaky_search_timeout_fix.sql.

Це серверне виправлення search_zagulyaky_people_v1 і
search_zagulyaky_documents_v1. Воно не змінює синхронізацію знахідок,
шлюби або статистику каталогу.

## Що виправлено

- Обгортки зберігають результат внутрішнього пошуку один раз
  (WITH source AS MATERIALIZED). Раніше обчислення повторювалося для
  items і nextCursor. Тест відтворює 2 виклики до зміни та 1 після неї.
- Загальна умова доступності записів стала NOT MATERIALIZED:
  повнотекстові й триграмні індекси відбирають збіги без попереднього
  збирання всього доступного каталогу. Прибрано чотири зайві з'єднання
  таблиці записів із собою.
- Фільтри ролі учасника й архіву виконуються без окремого виклику
  SECURITY DEFINER для кожного кандидата. Додано відповідні індекси.
- Курсор порівнюється як (published_at, id), дозволяючи одразу перейти
  до потрібної сторінки за індексом.
- Повторна перевірка приватності використовує UUID-індекс без id::text.
  Для географічних фільтрів явно вказана умова geo IS NOT NULL,
  необхідна для наявних часткових індексів.
- Оновлюється статистика планувальника (ANALYZE).

Ліміт часу самої функції залишився **5 секунд**. Очікування блокування
під час встановлення міграції обмежене через lock_timeout = 5s.

Пошук не обмежується «першими N записами каталогу»: ліміт кожної гілки
застосовується **після всіх фільтрів**. Рідкісні збіги, короткі імена,
архівні реквізити, буквальні %, _, \ та наступні сторінки збережені.

Приватність незмінна: лише published + cleared, а для потенційно живих
осіб — чинна згода, прив'язана до актуального вмісту. Прямий доступ
анонімних користувачів до таблиць і внутрішнього пошукового ядра не надається.
Немає видалення, перепублікації або масового переписування записів.

## Локальна перевірка

~~~powershell
node --test test/zagulyakySearchTimeoutFix.test.ts test/integration/zagulyakySearchDatabase.test.ts
npm.cmd test
npm.cmd run build
~~~

Інтеграційний тест виконує справжній SQL у PGlite/PostgreSQL з pg_trgm
та pgcrypto на вигаданих даних. Перевіряє одноразове виконання, однакові
результати старого й нового SQL для різних полів/фільтрів/спеціальних
символів/цитованих фраз, повноту пагінації без дублів, приватність,
зміну погодженого вмісту, ACL і валідацію аргументів.

Навантажувальна частина додає 50 000 записів і 50 000 учасників та
перевіряє справжній EXPLAIN ANALYZE, далеку сторінку й RPC у межах 5 с.
Орієнтир локального запуску на 50 220 записах: вибірковий RPC 19–30 мс,
порожній запит близько 5 мс, запити з 1–2 літер близько 164–179 мс.
Для вибіркових запитів план відвідував 1–2 записи основної таблиці;
відбір кандидатів скоротився приблизно з 53–111 до 16–21 мс.

Це **не заміри робочого Supabase**. Швидкість залежить від ресурсів,
розподілу даних, паралельних запитів і налаштувань PostgREST. Фікстура
не запускає весь стек Supabase та всі тригери запису/канонізації місць.

## Впровадження

Фронтенд, GitHub Pages, ключі та Edge Functions для цього виправлення
змінювати не потрібно. Новий SQL сумісний із чинними публічними RPC.

1. Спочатку застосувати міграцію до тестової бази з попередніми міграціями;
   перевірити пошук на репрезентативних даних.
2. Для робочої бази використати наявний процес міграцій:
   .github/workflows/deploy-supabase-functions.yml, крок
   **Apply database migrations** (supabase db push --linked --yes).
   Після публікації змін перевірити успішність саме цього кроку.
   Наявність файлу в GitHub або успіх GitHub Pages ще не доводить
   застосування SQL до бази.
3. Перевірити встановлення в Supabase SQL Editor:

~~~sql
select version
from supabase_migrations.schema_migrations
where version = '202609070001';

select
  position('with source as materialized' in pg_get_functiondef(
    'security_private.search_zagulyaky_people_v1(text,jsonb,integer,timestamptz,uuid)'::regprocedure
  )) > 0 as people_single_execution,
  position('with source as materialized' in pg_get_functiondef(
    'security_private.search_zagulyaky_documents_v1(text,jsonb,integer,timestamptz,uuid)'::regprocedure
  )) > 0 as documents_single_execution,
  position('eligible_rows as not materialized' in pg_get_functiondef(
    'security_private.search_zagulyaky_v1(text,text,jsonb,integer,timestamptz,uuid)'::regprocedure
  )) > 0 as indexed_candidate_search;
~~~

Очікується рядок версії та три true. Якщо SQL встановлювався вручну
поза менеджером міграцій, відсутність рядка версії не доводить відсутності
функцій: історію міграцій потрібно узгодити з фактично встановленим SQL.

4. Через сайт виконати по одному запиту: порожній, відоме прізвище,
   без збігів, роль/архів, наступна сторінка. Перевірити анонімний доступ
   і вхід у профіль. Не запускати масові повтори на перевантаженій базі.
5. Перевірити нові логи саме цих двох RPC: старі рядки 57014 залишаться.
   Якщо нові таймаути зберігаються, потрібні параметри запиту, план,
   поточні блокування/ресурси та застосовані індекси. Не вимикати
   таймаут чи перевірки приватності глобально.

Під час локальної розробки робоча база не змінюється автоматично.
