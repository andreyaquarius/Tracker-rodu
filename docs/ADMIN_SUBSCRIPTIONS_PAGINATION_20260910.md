# Нагальне виправлення списку підписок

## Гілки

- `codex/admin-subscriptions-pagination` створена від `main` (`9a1bc398`), без відкладених оптимізацій.
- Відкладені оптимізації збережено локальним комітом `79f7245a` у `codex/deferred-query-optimizations`. Цю гілку не потрібно зливати для виправлення підписок.
- Push, публікація сайту й зміни робочої бази під час реалізації не виконувалися.

## Зміна поведінки

Старий клієнт завантажував `admin_list_subscriptions()` одним запитом і рахував довжину отриманого масиву. Обмеження відповіді Data API могло обрізати список до 1000, після чого і лічильник, і локальний пошук працювали лише з цією тисячею.

Новий `admin_list_subscriptions_page_v1` повертає один JSON-об'єкт: повну кількість профілів, кількість за фільтрами та не більше 50 записів. Пошук і фільтри виконуються до пагінації. Сортування: адміністратори першими, далі дата створення профілю за спаданням і UUID для однозначного порядку. Завищена сторінка обмежується останньою наявною.

Обидва екрани адміністрування підписок використовують спільний компонент. Пагінація розміщена над і під таблицею; зміна фільтрів повертає на першу сторінку. Старі запити скасовуються, збереження підписки оновлює поточний результат і лічильники.

Семантика тарифів, пробного/безстрокового доступу й завершених підписок збережена. RPC залишається `SECURITY INVOKER` з перевіркою адміністратора та чинними RLS-політиками. Старий RPC не змінюється — попередній фронтенд залишається сумісним.

## Публікація

Потрібна тільки міграція `supabase/migrations/202609100000_admin_subscriptions_pagination.sql`. Вона додає RPC без зміни записів користувачів, тарифів або підписок. Ліміт Data API не підвищується.

Після коміту нагальних змін потрібно злити саме цю гілку в `main` і зробити Push. За поточними GitHub Actions, push у `main` запускає сайт і Supabase deployment окремо; дочекатися успіху обох. Push лише feature-гілки сам по собі ці production workflows не запускає.

Перевірити на сайті: повний лічильник, 50 рядків на першій сторінці, останню сторінку, пошук користувача поза першою тисячею. Кількість визначається таблицею `profiles`, як і в попередній версії, а не кількістю рядків поточної сторінки.

## Локальна перевірка

- PGlite: 1027 синтетичних профілів, 21 сторінка, остання містить 27 записів; усі UUID присутні рівно один раз.
- Пошук українською та за email, буквальні `%`, `_`, `\`, усі комбінації тарифів/статусів, порожній результат, зміна підписки й видалення записів між запитами.
- Недоступність RPC і загальних лічильників для `anon` та звичайного користувача; RLS залишається активною.
- Браузер: перехід на сторінку 21, пошук користувача 1026, синтетичне збереження, серверні фільтри, помилка завантаження та скасування повільного пошуку; темна тема, вузький iframe 390 px без горизонтального виходу сторінки.
- TypeScript і production build пройшли. Залишаються попередні попередження збірки про великі чанки.
- Повний набір: 2347 пройдено, 0 помилок, 5 пропущено. У старому тесті сумісності зв'язків нормалізовано CRLF/LF, щоб перевірка не залежала від Windows Git checkout; код зв'язків не змінено.

Це локальні перевірки, не підтвердження застосування міграції в production.
