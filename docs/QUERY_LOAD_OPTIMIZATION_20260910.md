# Оптимізація запитів — 10.09.2026

Зміни підготовлено локально за експортом Query Performance. Робочу БД, Realtime
publication, тариф, RLS і ліміти часу запитів не змінювали.

## Що змінено

- Каталог осіб: підрахунки лише для видимої сторінки/відкритої особи, запити до
  200 ID; кеш до 30 секунд у межах компонента/облікового запису; змінені пов'язані
  записи оновлюють лише зачеплені картки. Зміна сторінки/фільтра скасовує стару
  роботу, серія змін об'єднується за 150 мс. Сортування й фільтри лишаються
  глобальними: вони не залежать від цих допоміжних лічильників.
- SQL `list_person_summaries_v2`: обмежує всі агрегації вибраними особами, не
  обходить RLS. Індекс нормалізованих JSON-прив'язок зберігає сумісність зі старими
  знахідками, включно з великими літерами, пробілами й некоректними ID.
- Статистика «Загуляків»: та сама точна privacy-filtered функція за серверним
  кешем на 60 секунд. Зміни записів, джерел, учасників, місць і privacy clearances
  транзакційно роблять кеш неактуальним. У кеші тільки публічні числа/діапазони.
  Одночасні холодні читання об'єднуються; записи не беруть глобальний advisory
  lock: додають невеликий маркер на транзакцію, який прибирає наступне оновлення.
  Read-only/GET запити при промаху отримують точний результат без запису кешу.
- Зв'язки осіб: курсор `(updated_at DESC, id ASC)` замість зростаючих OFFSET;
  збережено проєктні фільтри, порядок і legacy-schema fallback.
- Дерево: однакові одночасні запити з однаковими версією графа й fingerprint
  доступу використовують один транспорт. Скасування окремого споживача не
  скасовує інших. Без fingerprint об'єднання заборонене.
- Підписка: об'єднання лише одночасних запитів у межах JWT/проєкту; ручне
  оновлення після оплати не читає застарілий збережений результат.
- Записи знахідок: зміна лише `updated_at` більше не перебудовує соціальні
  зв'язки. Реальні зміни, переміщення учасника, відв'язування, INSERT/DELETE й
  `RETURNING` залишають попередню поведінку. Пакетний імпорт уже був реалізований.

## Впровадження

1. Звірити стан міграцій робочої БД. Попередні виправлення
   `202609050002`, `202609070001`, `202609070002` мають бути застосовані;
   також потрібні попередні міграції контексту знахідок. Не запускати всі
   накопичені міграції без перевірки їхнього списку.
2. Спочатку перевірити на staging, потім застосувати міграції в порядку:
   - `202609100001_scoped_person_summaries.sql`
   - `202609100002_zagulyaky_public_stats_cache.sql`
   - `202609100003_skip_unchanged_finding_context_sync.sql`
   - `202609100004_zagulyaky_stats_safeupdate_compatibility.sql`
3. Створення GIN-індексу може блокувати запис у `findings` на час побудови.
   Обрати малонавантажений час і перевірити розмір таблиці на staging.
4. Опублікувати фронтенд. Якщо фронтенд випередив міграції, каталог використовує
   свої наявні локальні лічильники; він не повертається до дорогого повного RPC.
   Для точних серверних підрахунків міграція 001 обов'язкова.
5. Перевірити власника, редактора й читача: 1/2 сторінки каталогу, фільтри,
   повернення на попередню сторінку, перемикання облікового запису; велике дерево
   з усіма наборами батьків; шлюб/свідків, відв'язування і повторну прив'язку;
   публікацію та приховування «Загуляки» після прогріву кешу.

Старий `list_person_summaries` залишено для старих вкладок. Вони можуть продовжити
старі важкі запити до оновлення сторінки. Без дозволу не вимикати Realtime і не
видаляти `activity_log` із publication.

## Перевірка

```powershell
npm.cmd run build
npm.cmd test
node --test test/integration/queryLoadOptimizations.test.ts
node --test test/zagulyakyPublicStatsSafeupdate.test.ts
```

Інтеграційні тести виконують SQL у локальному PGlite на синтетичних даних:
еквівалентність старих/нових підрахунків, RLS, межі проєкту/200 ID, використання
GIN-індексу, ACL кешу, його інвалідацію та незмінність поведінки тригерів.
Це не заміна EXPLAIN і перевірки конкурентних транзакцій у робочому PostgreSQL.

## Виправлення `DELETE requires a WHERE clause` (004)

У міграції 002 очищення приватної черги інвалідації кешу було без `WHERE`.
Активний `pg-safeupdate` відхиляє такий запит з SQLSTATE `21000`, навіть якщо
зовнішній виклик — `SELECT public.get_zagulyaky_public_stats_v1()`.

Міграція 004 замінює лише приватну функцію кешування, додаючи умову
`where transaction_id is not null`. Це первинний ключ службової черги, тож
очищаються ті самі видимі маркери, а не особи, знахідки чи записи каталогу.
Зберігаються порядок «очистити → порахувати», MVCC-видимість, блокування лише
холодних читачів, TTL 60 секунд, read-only шлях, ACL та точна privacy-фільтрація.
Міграція не очищає кеш під час застосування і не вимикає захист бази.
Опубліковані міграції 001–003 залишено незмінними.

Перевірки:

- Node-контракт виявляє старий некваліфікований `DELETE` та перевіряє умову в 004;
  забороняє відключення захисту, `TRUNCATE` та видалення функцій/таблиць.
- PGlite виконує ланцюжок старої міграції та виправлення на синтетичних даних:
  холодний/теплий/прострочений кеш, усі три API-ролі, приватність, незмінність
  функціональних ACL, read-only, відкат очищення при помилці та повторний запуск.
  Маркер, доданий під час підрахунку, перевіряє порядок операцій; це не тест
  справжніх паралельних сесій PostgreSQL.
- `supabase/tests/zagulyaky_public_stats_safeupdate_test.sql` — окремий pgTAP-тест
  для локального/staging PostgreSQL із завантаженим `safeupdate`. Позитивні
  контролі перевіряють, що некваліфіковані DELETE/UPDATE справді відхиляються,
  а публічний RPC може оновити кеш. Усі тестові зміни відкочуються.
  Цей тест не призначений для робочої бази. PGlite не завантажує нативний модуль;
  під час підготовки Docker engine був недоступний, тому цей pgTAP-тест не виконано.
- GitHub Actions виконує Node-контракт та PGlite до підключення до робочої БД.
  Це доповнення, а не заміна перевірки з нативним `safeupdate` на staging.
- Два старі source-contract тести дерева/спільного доступу нормалізують CRLF
  під час читання, щоб однаково працювати на Windows і Linux. Їхні перевірки
  не послаблено; функціонал цих розділів не змінювався.

Результат локальної підготовки виправлення: `npm.cmd run build` — успішно;
`npm.cmd test` — 2 363 пройдено, 0 помилок, 5 пропущено (2 368 загалом).
Нативний pgTAP/safeupdate та застосування на робочій БД не виконувалися.

Публікація виправлення (не виконувалася під час локальної підготовки):

1. Залишити лише один механізм міграцій робочої БД. Якщо ним є GitHub Actions,
   вимкнути лише `Deploy to production` у Supabase GitHub Integration і
   дочекатися завершення вже активного запуску. Preview-гілки можна зберегти.
2. Commit/Push гілки виправлення → pull request → merge у `main`.
   Сам Push гілки не запускає production workflow, прив'язаний до `main`.
   Перезапуск старого невдалого workflow не міститиме міграції 004: GitHub
   повторює старий коміт. Потрібен новий запуск для коміту з виправленням.
3. Перевірити `Preview database migrations`: якщо 001–003 уже записані в історії
   бази, залишиться лише 004; якщо ні — CLI застосує відсутні міграції за порядком.
   Не редагувати вручну `supabase_migrations.schema_migrations`, не виконувати
   `migration repair --status applied`, `DROP FUNCTION` чи reset бази.
4. Дочекатися успішного `Apply database migrations` та `Deploy Edge Functions`.
   Перевірити RPC/статистику після закінчення TTL та після публікації/приховування
   тестового запису на staging. Перевіряти нові помилки, а не історичний рядок логу.

Читайте лише історію застосування, якщо потрібно звірити стан вручну:

```sql
select version, name
from supabase_migrations.schema_migrations
where version in ('202609100001', '202609100002', '202609100003', '202609100004')
order by version;
```

Порівнювати окремі однакові часові вікна: приріст `calls`, `total_exec_time`,
середній час, таймаути, CPU, RAM/Swap та кількість активних з'єднань. Історичні
мільйони викликів і 63,85% часу Realtime самі не зникнуть із накопиченої статистики.
Не скидати її перед збереженням базової вибірки. EXPLAIN ANALYZE для записів
виконує запис — проводити такі вимірювання на ізольованій staging-копії.
