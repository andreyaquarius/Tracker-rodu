# GeneHelp integration

Інтеграція GeneHelp працює через Supabase Edge Function `genehelp`.
Користувач не вводить і не бачить партнерський або інтеграційний токен.

## Як працює

1. Користувач натискає `Попросити допомоги в GeneHelp` у лівому меню.
2. Трекер Роду відкриває вікно з назвою та описом запиту.
3. Якщо користувач ще не підключений до GeneHelp, застосунок показує окремий
   екран згоди на передачу email та імені.
4. Edge Function `genehelp` перевіряє авторизованого користувача і не запускає
   onboarding без явного прапорця згоди.
5. Якщо для цього користувача ще немає GeneHelp integration token, функція
   реєструє або підключає його в GeneHelp через partner onboarding endpoint.
6. Отриманий `integration_token` шифрується через `ENCRYPTION_KEY` і
   зберігається в `user_genehelp_accounts`.
7. Запит про допомогу створюється в GeneHelp уже від імені конкретного
   користувача GeneHelp.

## Що потрібно налаштувати в Supabase

1. Застосувати SQL-міграцію:

   `supabase/migrations/202606250001_genehelp_onboarding.sql`

2. Переконатися, що в Supabase secrets є:

   `ENCRYPTION_KEY`

3. Додати partner token GeneHelp як Supabase secret. Функція читає ці назви:

   `PLAIN PARTNER TOKEN`

   або, якщо Supabase не приймає назву з пробілами:

   `PLAIN_PARTNER_TOKEN`

4. Розгорнути Edge Function:

   `genehelp`

У цьому репозиторії Edge Functions деплояться через GitHub Actions з
`.github/workflows/deploy-supabase-functions.yml`, якщо зміни потрапляють у
`main`.

## Історія надісланих запитів

Вікно GeneHelp має вкладку `Надіслані запити`. Вона показує локальну історію
запитів поточного користувача, які були створені через Трекер Роду.

Для цього потрібно застосувати додаткову SQL-міграцію:

`supabase/migrations/202606260001_genehelp_request_history.sql`

У таблиці зберігається тільки службова прив'язка до GeneHelp: id запиту,
назва, опис, статус, посилання та остання відповідь API. Самі роботи GeneHelp
виконуються й зберігаються на стороні GeneHelp.

## Зворотні сповіщення з GeneHelp

Трекер Роду отримує нові відповіді та зміни статусів через офіційний polling
API GeneHelp. У поточному партнерському контракті немає webhook і немає
окремого ACK endpoint: застосунок періодично читає стан GeneHelp, а повторна
обробка безпечно відсіюється локально за стабільним ідентифікатором події.

Опитування запускає дзвіночок сповіщень після відкриття, повернення фокусу до
вікна та під час його хвилинного оновлення. Клієнт викликає лише авторизовану
дію `sync-notifications` Edge Function `genehelp`; integration token ніколи не
передається у браузер і розшифровується тільки всередині Edge Function.
Серверний throttle не дозволяє одному користувачу запускати синхронізацію
частіше ніж раз на 45 секунд. Якщо GeneHelp не підключений або користувач ще не
створив через Трекер Роду жодного запиту, функція повертає успішний результат зі
станом `skipped` і не звертається до GeneHelp.

Edge Function використовує такі офіційні endpoint-и:

- `GET /api/partners/notifications?locale=uk&limit=100&page=N` — сторінки
  партнерських сповіщень. Обробляється лише тип
  `interaction_unread_message`; тип `ai_content` ігнорується.
- `GET /api/partners/genealogy-requests/minimal?page=N` — мінімальні дані
  запитів для звірки `status`, `public_status`, `visibility` та `updated_at`.
  Розмір сторінки цього endpoint-а за контрактом GeneHelp дорівнює 100.
- `GET /api/partners/v2/genealogy-requests?limit=100` — викликається лише тоді,
  коли повідомлення містить окремий ідентифікатор interaction без
  ідентифікатора запиту. Відповідь використовується тільки для встановлення
  відповідності interaction до genealogy request.

Пагінація перших двох endpoint-ів обмежена 20 сторінками за одну
синхронізацію. Усі відповіді GeneHelp перевіряються за очікуваною схемою та
розміром до використання. `target_url` не зберігається і не відкривається:
система приймає з нього лише ідентифікатори з канонічного шляху того самого
origin `https://genehelp.online`. Зовнішні, некоректні та неканонічні URL
ігноруються.

Перша успішна звірка статусу лише записує початковий стан запиту без
сповіщення, якщо локального надійного статусу ще немає. Надалі сповіщення про
статус створюється тільки за реальною зміною. Відповіді та зміни статусів
передаються до захищеної service-role RPC, яка перевіряє власника запиту,
відсіює дублікати та створює локальне сповіщення для правильного користувача.

## Тимчасове вмикання для користувачів

Кнопка `Попросити допомоги в GeneHelp` завжди видима адміністратору. Для інших
користувачів вона прихована, доки адміністратор не увімкне перемикач
`GeneHelp для всіх користувачів` у розділі `Тариф і підписка`.

Для адмінських перемикачів потрібно застосувати міграцію:

`supabase/migrations/202606260002_app_feature_flags.sql`

## Тестовий режим запитів

Зараз `geneHelpRequestTestMode = false`: запити надсилаються як звичайні.
Для окремої тестової інсталяції значення `true` додає `meta.is_test = true`.

Перемикач знаходиться в `supabase/functions/genehelp/index.ts`:

`geneHelpRequestTestMode`

## Валідація й діагностика відмов

Форма та браузерний сервіс перевіряють відомий локальний мінімум опису —
12 символів після trim, як у Edge Function. Це локальна умова; вона не
підтверджує повний набір правил стороннього API.

Якщо GeneHelp повертає `422` з полями `errors`, функція передає конкретні
пояснення користувачу замість загального `message`. Вміст форми залишається
на місці. Автоматичного повтору створення після `422` або мережевого збою немає.

До відповіді відмови додається фіксований технічний `code`: `GHONB` для
реєстрації/підключення користувача, `GHCRT` для створення запиту, `GHSTS` для
читання статусу, `GHSYN` для інших запитів синхронізації. Sentry отримує цей
код і HTTP-статус, але не пояснення валідації, поля форми чи ID запиту.

Для цих змін потрібне оновлення фронтенду та Edge Function `genehelp`.
Старі події Sentry без тіла відповіді не дозволяють визначити, яке саме поле
спричинило історичний `422`; це потрібно підтвердити конкретною відповіддю API.
