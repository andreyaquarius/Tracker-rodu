# Набори батьків і таймаути дерева — 07.09.2026

## Що підтверджено

Експорт користувача містить 50 записів: 26 помилок `57014` і 24 службові
повідомлення про checkpoint. У цьому експорті немає SQL-параметрів, ID дерева,
користувача чи плану виконання. Надані скриншоти вказують на
`get_family_tree_neighborhood_v1`. Точний план проблемного production-запиту
не перевірений; локальні заміри нижче не є замірами робочого Supabase.

## Виправлення

- «Усі набори батьків» має пріоритет над збереженим активним набором. При
  вимкненні повертається попередній вибір; він не стирається. Вибір одного
  набору недоступний, поки увімкнено показ усіх.
- Після перебудови зберігається екранна позиція фокусної картки, якщо немає
  явного якоря розгорнутої гілки. При зміні фокусної особи працює звичайне
  центрування. Дані людей/зв'язків не змінюються.
- Помилка початкового завантаження більше не прибирає панель параметрів:
  можна змінити глибину та повторити запит без виходу з модуля.
- Сумісність із відсутнім RPC (`PGRST202`/`42883`) збережена. Після таймауту,
  помилки доступу чи конфлікту версії запасний v1 не запускається:
  v2 вже викликає його всередині, тому повторювався той самий дорогий запит.
- Міграція `202609070002_family_tree_neighborhood_timeout_fix.sql` вмикає
  повторне використання планів лише в приватній реалізації обходу v1.
  Три CTE читання всього дерева стають `NOT MATERIALIZED`, щоб планувальник
  міг застосовувати індексовані умови дерева/особи до читання зв'язків.
  Решта алгоритму продовжень, сортування, курсори, точні лічильники,
  конфіденційність і права виконання не змінюються. Ліміти часу не збільшені.

Обґрунтування поведінки планів:
[PostgreSQL: plan_cache_mode](https://www.postgresql.org/docs/current/runtime-config-query.html#GUC-PLAN-CACHE-MODE).
Настройка функції відновлюється після виходу; глобальні настройки бази не змінюються.

## Перевірки

`node --test test/familyTreeParentSetToggle.test.ts test/integration/familyTreeNeighborhoodDatabase.test.ts`

Інтеграційний тест виконує реальні SQL-функції, графову DDL і нову міграцію
в ізольованому PGlite. Інфраструктура облікових записів зведена до тестових
членств; це не повний стек Supabase/PostgREST. Перевіряються:

- однакові відповіді до/після оновлення на 50 255 особах;
- 7 поколінь, кілька наборів батьків, спільні батьки, малі бюджети карток;
- предки, нащадки, партнери, брати/сестри, курсори, створені до оновлення;
- маскування живих осіб для читача; приховані, спростовані й конфіденційні
  зв'язки; відмова сторонньому користувачу та анонімному виклику;
- широка гілка з 2 479 дітьми, 600 повернених осіб і 1 880 прихованих дітей;
- незмінні ACL приватних функцій і відсутність витоку `plan_cache_mode` у сесію.

Один локальний прогін: ті самі 255 карток у дереві 50 255 осіб — **299 → 58 мс**;
широка гілка 2 480 осіб у дереві понад 52 тисячі — **221 → 115 мс**.
Показники залежать від середовища; багатокористувацьке навантаження/блокування
робочої бази тут не імітувалися.

Браузерна перевірка через computer-use на ізольованій сторінці з реальними
хуками та рендерером: класичне дерево, прямі предки, ширина 390 px,
багаторазове on/off, збережений вибір. Лічильник завантажень залишився **1**.
Після перемикання координати фокусної картки не змінилися; помилок консолі немає.
Сервіс збереження налаштувань у цій перевірці підмінений локальною заглушкою.

Фінальний `npm.cmd test` після доповнення розкладки: 2 321 успішних,
5 пропущених, 0 помилок (2 326 загалом). `npm.cmd run build` успішний; залишилося звичне попередження
про великі JS-бандли. `git diff --check` без помилок.

## Доповнення: стиснення й змішування гілок при показі всіх наборів

Скріншоти тестового frontend виявили окрему від таймаутів проблему геометрії.
У `directAncestorLayout.ts` перевірка `node.children.size > 2` повертала
`undefined`: третій унікальний батько навіть у далекому поколінні вимикав
рекурсивне розділення секторів **для всього дерева**. Залишалася щільна загальна
розкладка. Самої попередньої SQL-оптимізації для цього було недостатньо.

Тепер основна пара зберігає звичне центрування над дитиною, а додаткові
батьківські гілки отримують окреме місце за межами вже розміщених гілок.
Порядок: набір → батьки всередині набору, а не всі батьки → всі матері.
Враховуються повні межі піддерев і належних їм бічних гілок. Двоє батьків
із різних технічних записів зберігають стару геометрію; спільні батьки
семантичних наборів не перетворюються на дублікати.

Нові тести `test/familyTreeMultiParentLayout.test.ts` перевіряють:

- сім поколінь: 255 осіб без додаткових наборів, 299 з ними;
- окремі межі кожної сусідньої гілки, відсутність накладання карток;
- центр основної пари на кожному рівні в класичному дереві й прямих предках;
- on/off/on, переставлені вхідні масиви та попередні координати;
- однакові й частково спільні набори без дублювання, втрати зв'язків або кольорів.

Додатково перевірено реальний рендерер у браузері на цих штучних даних,
зокрема на вузькому полотні. Лічильник завантажень не змінюється при перемиканні.
Це не перевірка конкретної бази користувача зі скріншотів: її граф не надано.
**Ця правка геометрії потребує нового frontend, але не окремої SQL-міграції.**

## Впровадження

Локальна перевірка не застосовує міграцію до робочої бази й не публікує сайт.
Для випуску потрібні **і міграція, і новий frontend** через звичайний pipeline
проєкту. Не запускати тестові seed-запити на production.

Після застосування перевірити:

```sql
select version from supabase_migrations.schema_migrations
where version = '202609070002';

select n.nspname, p.proname, p.proconfig
from pg_proc p join pg_namespace n on n.oid = p.pronamespace
where n.nspname = 'public'
  and p.proname = 'get_family_tree_neighborhood_v1_feature_impl';
```

Очікується `plan_cache_mode=force_generic_plan`; публічні обгортки та їхній
контроль доступу мають залишитися чинними. На проблемному дереві перевірити
on/off із 7 поколіннями, перезавантаження сторінки, альтернативний набір,
розгортання гілки та нові записи журналу. Якщо таймаути повторюються, потрібні
ID дерева, параметри RPC, актуальний план виконання та перевірка очікування
блокувань; сам експорт цих даних не містить.
