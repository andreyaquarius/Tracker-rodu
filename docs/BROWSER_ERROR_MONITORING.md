# Моніторинг помилок браузера — Sentry

## Що вже підготовлено в коді

- Неперехоплені JavaScript-помилки та rejected promises; помилки сторінок React і родового дерева.
- Невдалі REST/RPC/Edge-запити основного клієнта Supabase, навіть якщо інтерфейс обробив помилку. Наприклад, `42501` у `table:projects`, `57014` у `rpc:get_family_tree_neighborhood_v1`.
- Технічні поля: код і категорія помилки, назва RPC/таблиці/Edge-функції, HTTP-статус, типовий маршрут без ID/slug, браузер/ОС, версія сайту, стек програмного коду.
- В адмін-панелі → «Безпека й аудит» є стан підключення та кнопка «Надіслати тестову помилку».
- Міграції Supabase та додаткові записи/опитування бази не потрібні. Невдалий запит не повторюється моніторингом.

Production-збірки вже налаштовані на наданий власником DSN у `.env.production` (проєкт `4512075160420432`, регіон `de`). Це публічна конфігурація, не секрет. Для вимкнення задайте `VITE_SENTRY_ENABLED=false` і перебудуйте сайт. `npm run dev` не надсилає звіти. Код сам не створює Sentry-акаунт, проєкт чи платну підписку.

## Діагностика невдалих Supabase-запитів

Нові поля додає клієнтський код до події Sentry автоматично. Налаштовувати їх вручну в Sentry чи змінювати базу Supabase не потрібно. Вони з'являться в **нових подіях після розгортання цієї версії сайту й оновлення вкладки**; старі події не доповнюються.

У Sentry відкрийте issue → конкретну подію → **Tags**:

| Поле | Значення та призначення |
| --- | --- |
| `failure_kind` | `transport` — `fetch` відхилив запит; `http` — отримана відповідь з HTTP-помилкою |
| `original_error_type` | Фіксований тип первинного винятку, наприклад `TypeError`, `TimeoutError`; невідомі назви стають `unknown`. Лише для `transport` |
| `network_start`, `network_end` | `online`, `offline`, `unknown` за `navigator.onLine` на початку та при завершенні запиту |
| `visibility_start`, `visibility_end` | `visible`, `hidden`, `unknown` на початку та при завершенні запиту |
| `pagehide_observed` | `yes`, якщо запит почався після `pagehide` або ця подія сталася під час нього; `no` — не спостерігалась; `unknown` — спостерігач недоступний |
| `request_duration` | Інтервал: `lt_100ms`, `100ms_1s`, `1s_5s`, `5s_30s`, `gte_30s`, `unknown` |

У **Contexts → supabase_request → duration_ms** міститься час від початку фактичного `fetch` до HTTP-відповіді або винятку, округлений до мілісекунд, з верхньою межею 24 години. Очікування в черзі та читання тіла відповіді сюди не входять; якщо годинник недоступний, поле відсутнє. Стан фіксується одразу при завершенні `fetch`, до асинхронного читання коду HTTP-помилки.

Приклади фільтрів у Sentry:

- `project:tracker-rodu-web failure_kind:transport network_end:offline`
- `project:tracker-rodu-web pagehide_observed:yes`
- `project:tracker-rodu-web original_error_type:TypeError visibility_end:visible`
- `project:tracker-rodu-web request_duration:gte_30s`

`online` не гарантує доступності Supabase, а `pagehide_observed:yes` не доводить, що саме закриття сторінки спричинило збій. Ці ознаки допомагають зіставити сценарії; вони не підмінюють мережевий діагноз. Після повернення сторінки з BFCache нові запити не успадковують старий прапорець `pagehide`, але запит, що пережив приховування та повернення, зберігає цю ознаку.

Де реалізовано:

1. `src/utils/supabaseRequestDiagnostics.ts` — знімки стану, тривалість і спостерігачі `pagehide`/`pageshow` у пам'яті. Вони ініціалізуються разом з моніторингом до відмальовування React. Обробник `pagehide` працює у capture-фазі, перед відправленням аналітики.
2. `src/utils/monitoredSupabaseFetch.ts` — додає діагностику до невдалого REST/RPC/Edge-запиту.
3. `src/services/supabaseAuth.ts` та `src/services/browserMonitoring.ts` — передають теги й контекст у Sentry.
4. `src/utils/browserMonitoringPrivacy.ts` — пропускає лише дозволені значення та числову тривалість. Діагностичні поля не змінюють fingerprint чи хвилинний ліміт однакових помилок.

Первинний текст винятку, URL, заголовки, токени, тіла запитів, ідентифікатори користувача та історія його дій не додаються. Звичайні `AbortError`, анонімний клієнт і приватні сторінки залишаються виключеними. Діагностика не повторює запити й не змінює їхній результат; це також не виправлення переривання аналітики при закритті вкладки.

## 1. Створити проєкт

1. Увійдіть у [Sentry](https://sentry.io/) та створіть проєкт для **React** у своїй організації.
2. Виберіть регіон зберігання і тариф відповідно до ваших потреб. Увімкнення платних функцій цим кодом не виконується.
3. Скопіюйте **DSN** зі сторінки налаштувань проєкту / Client Keys (DSN). Це публічна адреса приймання подій, не секретний токен керування.
4. У налаштуваннях безпеки даних проєкту вимкніть зберігання IP, увімкніть серверне очищення чутливих даних, обмежте доступ до звітів і перевірте строк їх зберігання. Мережеве з’єднання саме по собі розкриває IP постачальнику; клієнт не може цього приховати.

Інтеграція приймає hosted DSN для `o<number>.ingest.sentry.io`, `.ingest.us.sentry.io` та `.ingest.de.sentry.io`. Іншу адресу не додавайте до CSP довільно — для self-hosted інсталяції потрібне окреме налаштування.

## 2. Увімкнути в GitHub Pages

Наданий DSN уже записаний у `.env.production`, тому для звичайного GitHub Pages деплою додавати його в налаштування GitHub не потрібно. Workflow прибирає порожнє значення змінної перед запуском Vite, щоб воно не перекрило DSN із файлу.

За потреби змінити проєкт або вимкнути моніторинг: GitHub → Settings → Secrets and variables → Actions → **Variables**:

| Назва | Значення |
| --- | --- |
| `VITE_SENTRY_DSN` | Необов’язково: інший DSN замість значення з `.env.production` |
| `VITE_SENTRY_ENABLED` | `true` (або не задавати) |

Після коміту й push у `main` workflow збере сайт із цими значеннями. `.env.production` також потрібно включити в коміт. `VITE_SENTRY_ENVIRONMENT=production`, а release — SHA коміту. Додавання змінної без нової збірки не змінить уже опублікований JavaScript. Порожня GitHub-змінна DSN не вимикає моніторинг — для цього використовуйте `VITE_SENTRY_ENABLED=false`.

### Читабельні стеки TypeScript — рекомендовано

Додатково налаштуйте приватне завантаження source maps:

- **Variables:** `SENTRY_ORG` — slug організації; `SENTRY_PROJECT` — slug проєкту.
- **Secrets:** `SENTRY_AUTH_TOKEN` — токен для завантаження source maps/release у цей проєкт. Використовуйте build/organization token із найменшими потрібними правами за інструкцією Sentry.
- Ніколи не називайте секрет `VITE_SENTRY_AUTH_TOKEN`: усі `VITE_` значення доступні браузеру. Не надсилайте секрет у чат і не комітьте його.

Плагін завантажить вихідний код/source maps у Sentry, видалить `.map` із `dist`, а окрема перевірка заборонить публікацію, якщо файли карт залишилися. Не вимикайте цю перевірку. Без токена сайт і збір помилок працюють, але стек веде до мінімізованого JavaScript. Карти тоді взагалі не генеруються.

## 3. Якщо сайт розгортається через Vercel

Vercel також використовує DSN із `.env.production`. За потреби перевизначте змінні у Vercel → Project → Settings → Environment Variables для потрібного середовища й зробіть Redeploy. Для Preview задайте `VITE_SENTRY_ENVIRONMENT=preview`, щоб не змішувати тестові звіти з production, або `VITE_SENTRY_ENABLED=false`, щоб їх не надсилати. Release автоматично береться з `VERCEL_GIT_COMMIT_SHA`. Секрет `SENTRY_AUTH_TOKEN` також має бути лише серверною build-змінною.

## 4. Перевірити доставлення

1. Після успішного деплою відкрийте «Адміністрування → Безпека й аудит».
2. Має бути напис «Моніторинг увімкнено».
3. Натисніть «Надіслати тестову помилку». Вона не ламає сторінку й не змінює дані.
4. У Sentry → Issues знайдіть `Tracker Rodu monitoring test`. Звірте ID, release і environment.
5. Кнопка підтверджує передачу в SDK, а **не** доставлення на сервер: його підтверджує лише поява події у Sentry. Якщо події немає, перевірте DSN, CSP/Network, блокувальник реклами, ліміти Sentry та застосований build.
6. Для тесту справжнього падіння/невдалої RPC використовуйте тестове середовище, не змінюйте права чи записи робочої бази заради перевірки.

В Sentry налаштуйте сповіщення команді про нові production Issues, повторну появу виправленої помилки та сплеск подій. Ліміт і бюджет задаються також у самому Sentry; не покладайтеся лише на браузерний обмежувач.

## Приватність і обмеження

- Не збираються email, ім’я/ID користувача, дані родичів, записи, файли, поля форм, console breadcrumbs, cookies, Authorization, тіла запитів/відповідей, URL-параметри/фрагменти, місцеві змінні стека.
- Вільний текст повідомлення помилки замінюється технічною категорією: це свідомо обмежує подробиці, але стек, код і назва операції залишаються. Фільтрація виконується **до** відправлення, не лише в інтерфейсі Sentry.
- Session Replay, tracing, metrics, logs та автоматичний облік сесій вимкнені. Користувачі не отримують нових ідентифікаторів від нашого коду; цей моніторинг не є лічильником людей онлайн.
- Публічні bearer-сторінки `/shared-graph` виключені. Окремий анонімний клієнт цих сторінок не обгортається моніторингом.
- Помилки звичайного скасування запиту/необхідності повторного входу не надсилаються. REST-відмови доступу та таймаути надсилаються. HTTP-відмова, яку клієнт згодом успішно повторив, теж може з’явитися у звіті: вона не завжди означає остаточну помилку для користувача.
- Однакова подія надсилається не частіше разу на хвилину; максимум 30 звітів на завантаження сторінки. Це захист від циклу помилок, не гарантія повного обліку всіх інцидентів.
- Блокувальники, офлайн, закриття вкладки, аварія самого браузера або збій завантаження до запуску SDK можуть завадити звіту. Sentry не замінює журнали Supabase і перевірки доступності сайту.
- Технічний опис Sentry додано до обох варіантів сторінки конфіденційності. Перед production-увімкненням власник має перевірити налаштування постачальника, актуальну редакцію політики та умови обробки даних; сам код не гарантує юридичної відповідності.

## Вимкнення

Задайте `VITE_SENTRY_ENABLED=false` і перебудуйте/задеплойте сайт. Уже відкриті старі вкладки використовують попередню збірку до оновлення. Для негайного припинення приймання використовуйте керування Client Key/DSN у Sentry.
