## 4. Дати і роки

- `publishedAt` не містить придатної дати: у 2 132 елементів значення `null`,
  в одного елемента поле відсутнє;
- `dateText` зберігає локалізований текст Facebook, а не нормалізований
  timestamp;
- 1 994 елементи містять явно зазначений рік публікації;
- 139 елементів не містять року публікації;
- серед значень без року є дати поточного для Facebook року та відносні
  значення на кшталт кількості годин або днів;
- явно зазначені роки дописів охоплюють 2020–2026 роки.

`dateText` завжди потрібно зберігати без змін. Нормалізований `published_at`
можна записувати лише разом із джерелом визначення і точністю:

```text
exact
parsed_from_text
inferred_current_year
relative_unresolved
unknown
```

Поле `years[]` є лише підказкою для подальшого аналізу. Воно містить 1 690
значень у 1 425 дописах, але частина чисел є номерами справ, аркушів або
сторінок. У вибірці виявлено помилкові майбутні «роки» `2030`, `2052`, `2058`
і `2081`. Заборонено переносити `years[]` без контекстної перевірки у фактичні
дати публічного запису.

## 5. Архівні шифри

`archiveCodes[]` порожній у всіх 2 133 елементах, хоча щонайменше 334 тексти
містять ознаки архівного опису: назву архіву, фонд, опис, справу або аркуш.

Висновки:

- поточний extractor архівних шифрів не можна використовувати;
- вихідне порожнє поле зберігається в `raw_payload` для відтворюваності;
- архів, фонд, опис, справа, аркуш, сторінка і кадр мають виділятися в окремі
  поля новим parser/AI-процесом;
- результат завжди потребує перевірки користувачем або модератором.

Для кожного зображення у staging потрібно зберігати:

- Facebook photo ID;
- URL сторінки фотографії;
- початковий CDN URL;
- alt, ширину та висоту;
- статус отримання файла;
- MIME, розмір і SHA-256 фактично отриманого файла;
- приватний Storage path;
- статус перевірки прав на публікацію;
- посилання на дозволену публічну похідну копію, якщо вона створена.

Повторне зображення не завантажується вдруге після збігу photo ID або SHA-256.

Правила нормалізації:

1. Декодувати цільовий параметр `u` з `l.facebook.com/l.php`.
2. Зберігати і сирий URL, і декодовану ціль.
3. Видаляти лише відомі tracking-параметри, зокрема `fbclid`.
4. Не видаляти значущі параметри переглядачів FamilySearch та архівних систем.
5. Не переходити автоматично за скороченими URL без SSRF-захисту, контролю
   redirect chain, DNS/IP і максимального розміру відповіді.
6. Facebook UI, профілі та хештеги не позначати як історичне джерело.

## 9. Дублі й гранулярність записів

- повторів `postId` немає;
- повторів URL дописів немає;
- виявлено 9 груп нормалізованих текстових повторів, які охоплюють 23 дописи;
- виявлено щонайменше 146 груп повторних зображень;
- додаткові дублікати можливі через обрізаний текст, різні дописи про той самий
  документ і повторне використання одного джерела.

Первинний idempotency key:

```text
facebook_group_post:{postId}
```

Додаткові сигнали дублів:

```text
normalized_text_sha256
facebook_photo_id
downloaded_file_sha256
canonical_source_url
archive_reference
event_date + normalized_name + found_place
```

Один Facebook-допис може створити нуль, один або багато записів людей і
документів. Між staging-елементом та майбутніми записами потрібен зв'язок
many-to-many. Автоматичне злиття історичних осіб заборонене.

## 12. Приватність і правила публікації

1. Початковий JSON та всі його елементи завантажуються лише до приватного
   staging-шару.
2. Сирий текст, payload, автор Facebook, тимчасові CDN URL, приватні вкладення
   і технічні metadata не доступні `anon`.
3. Ім'я автора Facebook зберігається для provenance та модерації, але не
   публікується автоматично.
4. Авторство публічного запису в Трекері й авторство Facebook-допису є різними
   поняттями.
5. До публікації потрібно перевірити право на відтворення тексту й зображень.
6. За відсутності дозволу допускається публікація структурованих фактів,
   короткої цитати та посилання на джерело, але не повної копії допису чи
   скриншота.
7. Матеріал про можливу живу особу блокується до окремої ручної перевірки.
8. AI/OCR завжди створює чернетку; автоматична публікація заборонена.
9. Запис стає публічним лише після перевірки джерела, приватності, прав,
   дублів і рішення модератора.
10. Публічний API працює через окремі проєкції та не читає staging-таблиці.
11. Видалення або відкликання джерела не повинно стирати аудит. Публічний
    матеріал знімається, а технічна подія зберігається без зайвих персональних
    даних.

## 13. Правила безпечного імпорту

- імпорт виконується асинхронно й ідемпотентно;
- спочатку створюється batch у стані `draft`;
- перед записом перевіряються checksum, JSON shape і кількість елементів;
- кожен елемент зберігається окремою транзакційною операцією або контрольованим
  batch;
- помилка одного елемента не скасовує весь пакет;
- повторний запуск продовжує незавершений batch;
- у production-логах заборонено виводити `raw_text`, URL із токенами, імена та
  повні payload;
- service-role credential використовується лише серверним імпортером;
- до завершення dry run жоден staging-елемент не створює публічний запис;
- результат dry run має показати кількість створених, пропущених, помилкових,
  неповних і ймовірно дубльованих елементів.

## 14. Рішення щодо CSV

CSV для реалізації імпортера не потрібен. JSON є канонічним вхідним форматом,
оскільки без втрат зберігає вкладені масиви зображень, посилань і кандидатів
років.

CSV може використовуватися тільки як необов'язковий похідний звіт для ручної
перевірки в табличному редакторі. Він не повинен бути другим канонічним
джерелом і не повинен запускати окремий імпорт того самого набору даних.

Виняток: CSV необхідно окремо проаналізувати лише якщо підтверджено, що він
містить додаткові поля, відсутні в JSON.
